## 2024-03-17 - [CRITICAL] WebDAV handleMove and checkSamePath Null Pointer Dereference and Buffer Overflow
**Vulnerability:** A Denial of Service (DoS) vulnerability via Null Pointer Dereference in `handleMove` and a memory corruption/buffer overflow via invalid pointer arithmetic in `checkSamePath` existed when parsing the `Destination` header or path paths without slashes.
**Learning:** Functions like `strstr` and `strrchr` can return `NULL` if the character/substring is not found. Without `NULL` checks, subsequent pointer arithmetic (`NULL - string`) or `memmove` operations on these pointers cause fatal crashes. Additionally, using `strlen(source_path)` for VLAs inside a function can be unsafe if it is dynamically sized or calculated from unsafe operations.
**Prevention:** Always check pointers returned from string search functions like `strstr` and `strrchr` before dereferencing them. Avoid using Variable-Length Arrays (VLAs) in C++ when safe string manipulation techniques are available.
## 2024-05-24 - [Fix Authorization Bypass on ESP-IDF Webserver Handlers]
**Vulnerability:** Many ESP-IDF httpd handler functions (REST APIs, WebSockets, SSE, WebDAV) were missing `checkAuth()` verification, allowing an attacker to bypass authentication logic intended by the system.
**Learning:** In a C++ embedded webserver like `esp_http_server`, each URL handler needs independent verification of authentication requirements if middleware isn't centrally applying it. Additionally, WebSocket handlers process both HTTP handshakes and raw data frames in the same function. Applying authentication checks blindly at the top of a WebSocket handler corrupts the raw data frame by writing a 401 HTTP response into the socket stream.
**Prevention:** Always verify that every registered route handler implements the required authorization checks. For WebSocket handlers, carefully scope HTTP-level logic (like Auth headers) to the initial HTTP handshake block (`if (req->method == HTTP_GET)`).
## 2024-05-30 - [CRITICAL] Prevent Size_t Underflow When Checking Trailing Slashes
**Vulnerability:** A memory corruption vulnerability existed in `webDav.cpp:handleWebDav` when checking for a trailing slash using `pathName[strlen(pathName) - 1] == '/'`. If `pathName` was completely empty, `strlen(pathName)` evaluated to `0`, and subtracting `1` caused an unsigned integer underflow (to `size_t` max, `0xFFFFFFFF`), leading to out-of-bounds array access and a crash.
**Learning:** Checking the last character of a C-string requires guaranteeing the string is not empty. Without bounds checking on string length, array operations involving `strlen(str) - 1` are fundamentally unsafe.
**Prevention:** Always assert `strlen(str) > 0` before attempting to access `str[strlen(str) - 1]`.

## 2024-05-30 - [HIGH] Buffer Overflow in JSON Network List Building
**Vulnerability:** In `webServer.cpp:setupHandler`, `sprintf` was iteratively appending discovered Wi-Fi network information into `jsonBuff` using a `for` loop. Since no bounds checks were performed during iteration, a large number of Wi-Fi networks could exceed `JSON_BUFF_LEN`, overflowing the heap-allocated buffer.
**Learning:** Even if a buffer seems large (`JSON_BUFF_LEN` is 32KB), dynamically sized data from external environments (like nearby Wi-Fi SSIDs) must be bounded. `sprintf` provides no safety for this, and simply tracking a pointer `p` is insufficient without tracking remaining space.
**Prevention:** Iteratively appending strings into a shared buffer requires tracking remaining space. Use `snprintf` combined with remaining space subtraction (`rem -= n`) inside the loop body to ensure total appended data never exceeds buffer size.
## 2024-05-24 - Buffer Overflow in WebDAV header extraction

However, `extractHeaderVal` expects a destination buffer of size `IN_FILE_NAME_LEN` (128 bytes) and extracts up to `IN_FILE_NAME_LEN - 1` bytes without checking the actual destination buffer size, leading to a stack-based buffer overflow if an oversized `Depth` header is provided by a malicious client.

## 2024-05-24 - Prevent WebDAV Path Traversal
**Vulnerability:** A path traversal vulnerability was found in `webDav.cpp`. Both the requested path (`pathName`) and move destination (`dest`) were URL-decoded but not validated to prevent `../` sequences, allowing arbitrary file system access outside the designated WebDAV folder via HTTP methods like GET, PUT, MOVE, etc.

**Vulnerability:** A path traversal vulnerability was found in `webServer.cpp` and `webDav.cpp`. ## 2024-05-30 - [CRITICAL] Buffer Copy Over-Read/Write in WebDAV handleMove via `strlen(dest)`
**Vulnerability:** In `webDav.cpp:handleMove`, when removing the `/webdav` prefix from the destination path, `memmove(dest, pos + strlen(WEBDAV), strlen(dest))` was used. Using `strlen(dest)` as the size parameter for a `memmove` operation where `pos + strlen(WEBDAV)` is the source copies `strlen(dest)` bytes from a location further down the string, resulting in an over-read past the null terminator of the source string, and overwriting `dest` with garbage data.
**Learning:** In C/C++, when using `memmove`, `memcpy`, or similar functions to copy strings, never use `strlen(dest)` (the length of the destination buffer or the original unshifted string) as the size argument when copying a suffix of the string. This leads to undefined behavior, incomplete copies, or out-of-bounds reads/writes.
**Prevention:** Always base the size argument on the source string length (e.g., `strlen(pos + strlen(WEBDAV)) + 1` to include the null terminator).
## 2024-05-30 - [CRITICAL] Out-of-Bounds Read in WebDAV handleMove via Incorrect memmove Size
**Vulnerability:** In `webDav.cpp:handleMove`, an incorrect size argument was used in a `memmove` operation: `memmove(dest, pos + strlen(WEBDAV), strlen(dest))`. The size argument `strlen(dest)` refers to the length of the entire destination buffer, which is much larger than the remaining source string starting at `pos + strlen(WEBDAV)`. This causes an out-of-bounds read past the end of the source string, potentially copying garbage memory into the destination and causing memory corruption, crashes, or data leakage.
**Learning:** Using the length of a destination buffer as the copy size for string manipulation is a fundamental error. When copying a string from a source to a destination, the length must always be bounded by the source string length (including the null terminator if needed), not the destination length.
**Prevention:** In C/C++, when using `memmove` or `memcpy` to copy strings, always base the size argument on the source string length (e.g., `strlen(source_ptr) + 1` to include the null terminator). Never use `strlen(dest)` as the size argument.
## 2024-06-13 - [Buffer Underflow in parseJson]

## 2024-05-30 - [CRITICAL] Buffer Overflow in URL Encoding

However, it was only incremented when characters *required* encoding (`encodedLen += 3`). ## 2024-07-15 - [CRITICAL] NULL Pointer Dereference and Typo in sizeof()
**Vulnerability:** In `telegram.cpp:searchJsonResponse`, there were two vulnerabilities:
1. `char* endItem = strchr(startItem, ',');` was followed directly by `int valSize = endItem - startItem;`. If the JSON did not contain a `,` (e.g., if it was malformed or the last item in the object), `strchr` would return `NULL`. The subsequent pointer arithmetic `NULL - startItem` would underflow, leading to an out-of-bounds memory read (or crash) during the `strncpy` operation.
2. A typo in the bounds check `valSize = sizeof(keyValue - 1);` resulted in taking the size of a pointer (`char*`) rather than the array minus one. This would silently truncate any value longer than 4 (or 8) bytes to 4 (or 8) bytes, breaking functionality.
**Learning:** Never assume string searching functions like `strchr` or `strstr` will successfully find the character/substring in untrusted input like JSON responses. Failing to check for `NULL` before pointer arithmetic is a classic cause of crashes and out-of-bounds memory corruption. Furthermore, typos in `sizeof` parameters can be syntactically valid (due to array decay to pointer) but logically disastrous.
**Prevention:** Always verify the return value of `strchr` or `strstr` is not `NULL` before using it in pointer arithmetic or string operations. Use robust JSON parsing libraries if available, or ensure manual parsing correctly handles edge cases (like the end of an object `}` or the end of the string). Always double-check `sizeof` usage to ensure you are taking the size of the *buffer* and then subtracting, i.e., `sizeof(buffer) - 1`, not `sizeof(buffer - 1)`.
